# 평가셋

## 관련도 분류 (`classify-labels.jsonl`)

2026년 10~11월에 13개 소스에서 모은 글 81건 중 50건에 사람이 직접 라벨을 달았다. 보류 판정 글은 모두 넣고, 저장 · 버림은 소스가 고르게 섞이도록 뽑았다.

- 라벨: `save`(수집 기준에 맞는 엔지니어링 글), `inbox`(경계라 사람이 판단할 글), `drop`(기준 밖)
- `memo`: 라벨을 고친 이유. 기준을 다듬을 때 참고한다.
- 글 본문은 넣지 않는다(공개 레포 · 저작권). URL로 `ctx collect --out` 결과와 이어 붙여 평가한다.

```bash
uv run ctx collect --days 30 --out /tmp/articles.jsonl
uv run ctx eval-classify eval/classify-labels.jsonl --articles /tmp/articles.jsonl
# 이미 분류한 결과만 채점할 때 (Claude를 다시 부르지 않는다)
uv run ctx eval-classify eval/classify-labels.jsonl --decisions /tmp/classified.jsonl
```

지표:

- **저장 정밀도**: 저장으로 고른 글 중 정답도 저장인 비율. M1 완료 기준은 80% 이상.
- **놓친 글**: 정답이 저장인데 버린 글. 가장 피할 실수라 따로 센다.
- **일치율**: 저장 · 보류 · 버림이 정확히 맞은 비율. 참고용.

## M0 결과 (2026-11-05, Claude Sonnet, 20건씩 묶어 호출)

| 기준 · 경계값 | 일치율 | 저장 정밀도 | 놓친 글 |
|---|---|---|---|
| 처음 기준, 보류 0.4 · 저장 0.7 | 78% | 100% | 2 |
| 바꾼 기준, 보류 0.4 · 저장 0.7 (2회) | 82%, 78% | 100% | 0 |
| **바꾼 기준, 보류 0.3 · 저장 0.6 (현재 기본값)** | **88%** | **100%** | **0** |

- **바꾼 기준**: 검색 · 추천 시스템 엔지니어링(효과 측정, 임베딩 · 모델 통합과 비용, 서빙)을 수집에 넣었다. 학습 데이터 합성 · 개인화 ML 플랫폼 · 결정 사례 없는 동향 글은 경계(`borderline`)로, ML 모델링은 모델 아키텍처 · 비전 · 음성 모델 · 논문 구현으로 좁혔다. 처음 기준은 추천 효과 측정, 파운데이션 모델 통합 글을 버렸다.
- 바꾼 기준에서는 **어긋난 글이 모두 한 칸 차이**다(저장 ↔ 보류, 보류 ↔ 버림). 저장할 글을 버리거나 버릴 글을 저장한 경우는 없다.
- **출력 안정성**: 호출 14회(81건 분류 5회, 평가 3회 × 3)에서 JSON 오류 · 빠진 판정 0건. 같은 입력을 다시 돌리면 일치율이 4%p 안팎으로 흔들린다.
- **한계**: 50건에 맞춘 경계값이다. 수집이 쌓이면 Inbox 피드백으로 평가셋을 늘려 다시 보정한다.

## 직군 기준 (2026-11-10, Claude Sonnet)

직군 기준(plan 5.1)을 같은 라벨로 채점했다. 45일 수집으로 50건 중 46건의 본문을 받았다. 라벨은 예전 기준(백엔드 · 인프라 · 데이터를 한 주제로, 검색 · 추천 측정을 수집으로)으로 달았다.

| 기준 | 일치율 | 저장 정밀도 | 저장 재현율 | 놓친 글 |
|---|---|---|---|---|
| 예전 기준 (주제 직접 적음) | 85% | 95% | 87% | 0 |
| 백엔드 · 프론트엔드 · AI | 70% | 94% | 65% | 4 |
| **+ 인프라 · 데이터 (현재 기본값)** | **74%** | **95%** | **78%** | **2** |

- 7개를 모두 고르면 재현율이 예전 기준과 같다. 직군 기준이 글을 놓치는 게 아니라 고른 범위만큼 남긴다.
- 기본값에서 놓친 2건(추천 효과 측정, 파운데이션 모델 통합)은 ML 직군으로 옮긴 주제다.
- 직군 3개 조합은 인프라 · 데이터 글(컨테이너 격리, 지표 시맨틱 레이어)까지 버려서 기본값을 5개로 정했다.
- 7개 조합의 정밀도 하락은 비전 인코더 · CVE 추적 글을 저장한 탓이다. ML · 보안을 고른 사람에게는 맞는 판정이라 라벨을 직군별로 다시 달아야 정확히 잴 수 있다.

## 검색 (`search-queries.yaml`)

`ctx init`으로 채운 위키(저장 209건 + 보류 77건)에 질의 57개를 만들어 사람이 정답을 확인했다.

- `ko-en` · `en-ko`: 한국어로 영어 글을, 영어로 한국어 글을 찾는 질의 (각 10)
- `detail`: 제목이 아니라 본문 세부 내용을 묻는 질의 (6)
- `topic`: 같은 주제의 여러 글 중 하나를 찾는 질의 (8)
- `paraphrase`: 글과 겹치는 단어를 피해 바꿔 말한 질의 (20)
- 답 없음: 위키에 답이 없는 질의 (3). 결과 없음 기준을 정할 때 쓴다.

```bash
# 비교할 모델마다 원문 단락 벡터를 먼저 만든다 (설정은 바꾸지 않는다)
uv run ctx reembed --model minilm --model e5-small --model bge-m3 --no-switch
uv run ctx eval-search eval/search-queries.yaml --models minilm,e5-small,bge-m3
```

## 검색 결과 (2026-11-06, recall@5)

| 방식 | 전체 | detail | en-ko | ko-en | paraphrase | topic | 1위 유사도 (답 있음 중앙값) | 1위 유사도 (답 없음 최댓값) |
|---|---|---|---|---|---|---|---|---|
| 키워드만 | 42/54 | 6/6 | 10/10 | 9/10 | 10/20 | 7/8 | - | - |
| paraphrase-multilingual-MiniLM | 44/54 | 6/6 | 10/10 | 8/10 | 13/20 | 7/8 | 0.67 | 0.71 |
| multilingual-e5-small | 42/54 | 6/6 | 8/10 | 7/10 | 13/20 | 8/8 | 0.89 | 0.90 |
| **bge-m3 (기본값)** | **48/54** | 6/6 | 10/10 | **10/10** | **14/20** | 8/8 | 0.64 | 0.60 |

- 모델 검색은 키워드 검색과 RRF로 합친 결과다. 키워드만 써도 한↔영 질의는 잘 찾는다. 요약 · 태그가 한국어 · 영문으로 함께 있어서다.
- 차이는 바꿔 말한 질의에서 난다. bge-m3는 키워드 검색보다 4건 더 찾고, 다른 종류에서 잃는 질의가 없다.
- e5-small은 한↔영 질의에서 키워드 검색보다 나빠진다. 의미 점수가 고르게 높아(0.8~0.9) 순위를 흐린다.
- **결과 없음 기준**: 세 모델 모두 답 없는 질의의 1위 유사도가 답 있는 질의와 비슷하거나 높다. 기준값을 두지 않는다.
- **질의 단어 포함률도 안 된다** (2026-11-09, bge-m3): 질의를 나눈 검색 단위가 글에 든 비율을 상위 5개 글에서 재고 가장 높은 값을 봤다. 답 있는 질의는 최저 0.22 · 중앙값 0.67, 답 없는 질의(평가셋 3개 + 따로 만든 5개)는 0.38~0.80이라 겹친다. MCP는 판단을 호출한 Claude에 맡긴다 (plan 8장).
- **bge-m3가 놓친 질의 6개**: 영어로 바꿔 말한 질의 4개(한국어 글을 찾는 질의), 협력사 장애 대비 연동, GPU 나눠 쓰기.

## MCP 결정 질문 (`decision-queries.yaml`)

기술 결정을 앞둔 Claude가 물을 법한 문제 서술 23개다. 답 있음 18개, 답 없음 5개.

- 20개는 위키의 결정 기록 198건에서 분야가 겹치지 않게 골라 만들고, 사람이 원문과 대조해 질문과 정답을 고쳤다.
- 3개는 사람이 실제로 고민했던 결정이다(MSA 위험 지표, Spring Batch 도입 규모, 서비스 간 데이터 동기화). Spring Batch는 도입 기준을 다룬 글이 없어 답 없음이다.
- `claude_calls`: Claude Code에 질문만 줬을 때 실제로 보낸 `find_decision_cases` 입력(topic · problem). 6건.

```bash
uv run ctx eval-mcp eval/decision-queries.yaml
```

세 가지로 잰다. 위키 내용은 출력하지 않는다.

- `find_decision_cases(problem=질문)`, `search_wiki([질문])`: 질문 그대로 넣는다.
- Claude 호출: `claude_calls`를 그대로 다시 넣는다. Claude가 topic을 붙이거나 자기가 아는 해법으로 질의를 바꾸는 경우를 잰다.

- **놓쳤던 호출**: 서비스 간 데이터 동기화. Claude가 topic "서비스 간 데이터 동기화"와 problem(CDC · outbox 비교)을 줬다. problem만으로는 정답이 1위인데, 짧은 topic을 따로 검색하면 "데이터 동기화" 낱말만 맞는 다른 글이 올라와 합친 순위에서 9위로 밀렸다. 한 질의로 묻게 바꿨다.
- **한계**: 질문 대부분을 결정 기록을 보고 만들어 단어가 겹친다. 질문 그대로 넣은 두 줄은 상한에 가깝다. MCP 질의 로그에서 실제 호출을 모아 `claude_calls`를 늘린다.

- 웹 검색을 막아서 `suggest_source`는 확인하지 못했다.
